# ADR 0004: How the User service works (profiles, ids, sync with Auth)

- Status: **accepted by delegation** (owner said "it is your call" for improving the User service); reversible, the service did not run before.
- Date: 2026-11-22
- Scope: `backend/c#/OmniCore.Services.User/**`
- Related findings: U1, U2, U3, U5, U6, UD1-UD8, UA1-UA6, UI1 in `docs/repo-check.md`

## Context

The User service was a design: no database, no endpoints, no wiring. Its commands took the user id and tenant id from the
request body (U3), nothing created a profile when an account registered (U6), the tenant-profile command returned success
without saving (U2), and two handlers would have failed on save (UA1). ADR 0001 (multi-tenancy) is still waiting for the owner.

## Decision

1. **The profile id is the Auth account id.** There is no foreign key across the two databases; the id is the link.
2. **Profiles are created only by the broker**, from `AccountRegisteredIntegrationEvent` (Auth.Contracts), through an internal
   `ProvisionUserProfileCommand`. There is no public "create profile" endpoint, so nobody can create a profile for another id.
   The handler is idempotent (a profile that exists is a success), because the broker can deliver twice.
3. **The caller is always the token.** Every endpoint under `/api/v1/users/me/...` acts on the signed-in user; commands carry no user id.
   Reading another user is `GET /{id}` (public fields only) and `GET /{id}/details` (admin only).
4. **User name and e-mail are display copies; Auth stays the source of truth.** They are not unique in the User database
   (Auth allows `Alice` and `alice`, AI1, and a unique index here would make the consumer fail and retry forever). E-mail is optional because Auth's is.
   Keeping them in step needs more Auth events (AC1); that is a later change.
5. **The aggregate owns its children.** Settings and addresses change only through `UserProfile` methods that validate (theme
   `Light|Dark|System`, language code, address limits, one primary address, at most 10 addresses).
6. **Tenant profiles are not built.** `UserTenantProfile` stays in the domain but is not mapped to the database and has no use case or
   endpoint until the owner answers ADR 0001. The stub command that returned success without saving is removed.
7. **Schema** `users` in its own database (`USER_DB_NAME`), tables `user_profiles`, `user_settings`, `user_addresses` plus the MassTransit
   outbox/inbox tables. The first migration is generated by CI (`dotnet ef`), not written by hand.
8. **Avatars** are checked by file signature (JPEG, PNG, WebP), not only by the client's content type (U5).

## Consequences

- Profile data exists only after Auth publishes the event; accounts registered before this change have no profile (a one-off
  backfill would need a list of accounts from Auth, not part of this ADR).
- Removing a profile or an account is not handled yet (AD2/AC1).
- The service can be started in compose and covered by CI like Auth; the full stack is still not started as a whole.
